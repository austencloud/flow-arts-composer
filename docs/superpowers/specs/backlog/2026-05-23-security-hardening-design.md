## Problem

A comprehensive audit surfaced 9 security findings across API endpoints, Firestore rules, and infrastructure. Two are critical (unauthenticated mutation of cloud storage and Firestore), one enables query injection, and two allow resource exhaustion. The remaining four are defense-in-depth gaps.

## Findings

### Critical

#### 1. QR video upload has zero authentication

**File:** `src/routes/api/qr-video/[hash]/+server.ts` (lines 6-32)

The `PUT` handler validates the hash format and enforces a 20 MB size limit, but never checks who the caller is. Anyone on the internet can upload arbitrary 20 MB files to the R2 `QR_VIDEOS` bucket.

```ts
// Current — no auth check anywhere
export const PUT: RequestHandler = async ({ params, request, platform }) => {
  const hash = params.hash;
  if (!hash || !HASH_RE.test(hash)) { ... }
  // ...uploads directly to R2
  await bucket.put(`qr-videos/${hash}.mp4`, body, { ... });
};
```

**Fix:** Add `requireFirebaseUser` at the top of the handler. Optionally verify the caller owns the shortcode whose hash they are uploading to (query `shortcodes` collection where `videoHash == hash`).

```ts
import { requireFirebaseUser } from "$lib/server/auth/requireFirebaseUser";

export const PUT: RequestHandler = async (event) => {
  const caller = await requireFirebaseUser(event);

  const hash = event.params.hash;
  if (!hash || !HASH_RE.test(hash)) {
    return new Response("Invalid hash", { status: 400 });
  }

  // ...rest of existing logic
};
```

Add rate limiting with `RATE_LIMITS.GENERAL` or a new `QR_UPLOAD` preset.

#### 2. `appMetrics` Firestore collection is world-writable

**File:** `firestore.rules` (lines 996-1004)

```
match /appMetrics/{metricId} {
  allow read: if true;
  allow write: if true;   // <-- line 1003
}
```

The comment says "atomic increment of totalGenerated counter" but the rule allows `create`, `update`, and `delete` of any document in the collection. An unauthenticated user can overwrite the counter to any value, create arbitrary documents, or delete existing ones.

**Fix:** Replace the blanket `write: if true` with a constrained update rule that only allows incrementing a specific field by 1. Disallow create and delete from clients entirely (use Admin SDK for initialization).

```
match /appMetrics/{metricId} {
  allow read: if true;

  // Only allow incrementing totalGenerated by exactly 1
  allow update: if request.resource.data.diff(resource.data).affectedKeys().hasOnly(['totalGenerated'])
    && request.resource.data.totalGenerated == resource.data.totalGenerated + 1;

  allow create, delete: if false;
}
```

If other metric fields need client-side writes, enumerate them explicitly in the `affectedKeys()` check and constrain their deltas.

### High

#### 3. HogQL injection via userId interpolation

**File:** `src/routes/api/admin/analytics/+server.ts` (lines 81-156)

Four query-building functions (`buildEngagementQuery`, `buildActivityQuery`, `buildContentQuery`, `buildSessionsQuery`) interpolate `userId` directly into HogQL strings via template literals:

```ts
// Line 87
WHERE distinct_id = '${userId}'
```

The regex on line 178 (`/^[\w.-]+$/`) allows `.` and `-`, which is broader than Firebase UID format (alphanumeric only, 28 chars). While PostHog's HogQL parser may not be exploitable the same way SQL is, string interpolation into any query language is a vector. A crafted userId containing `'` (if the regex were to loosen) would break out of the string literal.

**Fix:** Use parameterized queries. PostHog's HogQL API supports placeholders:

```ts
async function executeHogQLQuery(
  query: string,
  values?: Record<string, string | number>
): Promise<{ results: unknown[][] } | null> {
  const projectId = getProjectId();
  const response = await fetch(
    `${POSTHOG_API_BASE}/projects/${projectId}/query/`,
    {
      method: "POST",
      headers: getPostHogHeaders(),
      body: JSON.stringify({
        query: {
          kind: "HogQLQuery",
          query,
          values: values ?? {},
        },
      }),
    }
  );
  // ...
}
```

Then rewrite each builder to use placeholders:

```ts
function buildEngagementQuery(): { query: string; values: Record<string, string> } {
  return {
    query: `
      SELECT max(timestamp) as last_active,
             count(distinct $session_id) as sessions_count
      FROM events
      WHERE distinct_id = {userId}
        AND timestamp > now() - interval 30 day
    `,
    values: {},  // userId passed at call site
  };
}
```

At the call site, merge `{ userId }` into the values object. Also tighten the regex to `/^[a-zA-Z0-9]+$/` and enforce `userId.length <= 128`.

If PostHog's HogQL API does not support parameterized values, keep the regex but additionally escape single quotes in userId (`userId.replace(/'/g, "\\'")`) and add a strict allowlist regex (`/^[a-zA-Z0-9]{1,128}$/`).

#### 4. `scanEvents` recursive wildcard allows creation under any parent path

**File:** `firestore.rules` (lines 922-926)

```
match /{path=**}/scanEvents/{eventId} {
  allow read: if isAdmin();
  allow create: if true;
  allow update, delete: if false;
}
```

The `/{path=**}` wildcard means this rule matches `scanEvents` as a subcollection under ANY document path, not just `shortcodes/{code}/scanEvents`. An unauthenticated user can create documents at paths like `users/{anyUid}/scanEvents/{id}` or `__admin__/config/scanEvents/{id}`.

**Fix:** Replace the recursive wildcard with the explicit parent path. Move the collectionGroup read authorization to a separate rule or use a Cloud Function for the admin live feed.

Option A -- explicit parent path + collectionGroup read:

```
// Nested under shortcodes
match /shortcodes/{code}/scanEvents/{eventId} {
  allow create: if true;
  allow read: if isAdmin();
  allow update, delete: if false;
}
```

For the admin collectionGroup query, either:
- Use Admin SDK (bypasses rules) from a Cloud Function, or
- Add a collectionGroup-scoped rule that only allows admin reads:

```
match /{path=**}/scanEvents/{eventId} {
  allow read: if isAdmin();
  allow create, update, delete: if false;
}
```

This keeps the collectionGroup query working for admins while restricting creation to the correct parent path.

Option B -- if client-side collectionGroup queries are needed from the admin dashboard, keep both rules. The nested rule handles create; the collectionGroup rule handles admin read only.

#### 5. `tika/sequence` and `batch-render` accept unbounded CPU work, no auth

**Files:**
- `src/routes/api/tika/sequence/+server.ts` (lines 366, 403)
- `src/routes/api/batch-render/+server.ts` (lines 119-218)

`tika/sequence` accepts `maxAttempts` from the request body with no upper bound:

```ts
// Line 366 — interface allows any number
maxAttempts?: number;

// Line 403 — defaults to 100 but accepts any value
const maxAttempts = body.maxAttempts ?? 100;
```

A caller can set `maxAttempts: 1_000_000` and force the server into a long-running loop (line 180: `for (let attempt = 0; attempt < maxAttempts; attempt++)`).

Both endpoints have rate limiting (`RATE_LIMITS.GENERAL` / `RATE_LIMITS.AI_RENDER`) but neither requires authentication. Combined with the in-memory rate limiter (Finding 6), an attacker can exhaust CPU across multiple Worker isolates.

**Fix for tika/sequence:** Clamp `maxAttempts` to a hard ceiling:

```ts
const MAX_ATTEMPTS_CEILING = 200;
const maxAttempts = Math.min(body.maxAttempts ?? 100, MAX_ATTEMPTS_CEILING);
```

**Fix for both endpoints (auth):** Add `requireFirebaseUser` to both handlers. If anonymous access is intentionally needed for the landing page demo, add a separate unauthenticated endpoint with a much lower rate limit and a hard cap on input complexity (e.g., max 4 letters, maxAttempts locked to 50).

### Medium

#### 6. In-memory rate limiter resets per Worker isolate

**File:** `src/lib/server/security/rate-limiter.ts` (lines 15-28)

```ts
// In-memory store (cleared on server restart)
const rateLimitStore = new Map<string, RateLimitEntry>();
```

Cloudflare Workers spin up multiple isolates. Each isolate gets its own `Map`, so an attacker hitting different edge locations (or even the same location at scale) can bypass rate limits by getting routed to fresh isolates.

**Fix:** Replace the in-memory `Map` with Cloudflare KV or a Durable Object counter.

- **KV approach** (eventual consistency, simpler): Store `${prefix}:${identifier}` keys with TTL matching `windowMs`. Use `get`/`put` with expiration. Accept that counts may be slightly off due to KV's eventual consistency.
- **Durable Object approach** (strong consistency, more complex): Create a `RateLimiterDO` that holds the counter in-memory with a single point of truth per identifier.

For most endpoints, KV is sufficient. For auth-sensitive endpoints (`ACCOUNT_SENSITIVE`, `AUTH_ATTEMPTS`), use a Durable Object.

Interim mitigation: Add Cloudflare WAF rate limiting rules at the edge (Zero Trust > Security > WAF > Rate limiting rules) for the most sensitive paths (`/api/qr-video/*`, `/api/admin/*`, `/api/tika/*`).

#### 7. Feedback ingest API key in query string

**File:** `src/routes/api/feedback/ingest/+server.ts` (lines 4, 64-65)

```ts
// Line 4 — documented in the endpoint header
// GET /api/feedback/ingest?key=<SECRET>&title=...

// Line 64-65
const key = event.url.searchParams.get("key");
if (!key || key !== FEEDBACK_INGEST_KEY) { ... }
```

Query parameters appear in access logs, CDN logs, browser history, and Referer headers. The API key is effectively leaked to any log aggregator.

**Fix:** Move the key to an `Authorization` header or `X-API-Key` header. Switch from GET to POST to avoid URL logging entirely.

```ts
export const POST: RequestHandler = async (event) => {
  const apiKey = event.request.headers.get("x-api-key");
  if (!apiKey || apiKey !== env.FEEDBACK_INGEST_KEY) {
    return json({ ok: false, error: "Invalid or missing API key" }, { status: 401 });
  }

  const body = await event.request.json();
  // ...parse title, description, etc. from body instead of query params
};
```

Update all callers (LLM agents, scripts) to send the key in a header.

#### 8. CSP uses `unsafe-inline` and `unsafe-eval`

**File:** `src/hooks.server.ts` (lines 83-99)

```ts
"script-src 'self' 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' ...",
```

`unsafe-inline` defeats XSS protection for inline scripts. `unsafe-eval` allows `eval()` and `Function()` constructors.

**Fix (incremental):**

1. **Remove `unsafe-eval`** if no code relies on `eval()`. Vite's dev mode needs it, but production should not. Use a conditional CSP:

```ts
const scriptSrc = dev
  ? "script-src 'self' 'unsafe-inline' 'unsafe-eval' 'wasm-unsafe-eval' ..."
  : "script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval' ...";
```

2. **Replace `unsafe-inline` with nonces** (longer-term). SvelteKit supports CSP nonces via `%sveltekit.nonce%` in `app.html` and the `csp` config in `svelte.config.js`. This is a larger migration because all inline event handlers and `<style>` blocks need updating.

3. **Keep `wasm-unsafe-eval`** -- required for WASM modules (Three.js, etc.).

#### 9. `followerCount` update rule allows count manipulation

**File:** `firestore.rules` (lines 291-298)

```
allow update: if isOwner(userId)
  || isAdmin()
  || (isAuthenticated()
      && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['followerCount'])
      && request.resource.data.followerCount == resource.data.followerCount + 1)
  || (isAuthenticated()
      && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['followerCount'])
      && request.resource.data.followerCount == resource.data.followerCount - 1);
```

The rule constrains the delta to +1/-1 and locks the affected key, which is good. However, it does not verify that a corresponding `following/{userId}` or `followers/{followerId}` document was created/deleted in the same batch. An authenticated user can increment any other user's followerCount by 1 per request indefinitely without actually following them, or decrement it to 0.

**Fix:** Move followerCount updates to a Cloud Function triggered by writes to the `following` subcollection. Remove the direct client-side followerCount update rule.

```
// Remove the followerCount clauses from the update rule:
allow update: if isOwner(userId) || isAdmin();
```

Create a Cloud Function:

```ts
// functions/src/onFollowChange.ts
export const onFollowWrite = onDocumentWritten(
  "users/{userId}/following/{followedId}",
  async (event) => {
    const followedId = event.params.followedId;
    const change = event.data;

    if (change?.after.exists && !change?.before.exists) {
      // New follow — increment
      await db.doc(`users/${followedId}`).update({
        followerCount: FieldValue.increment(1),
      });
    } else if (!change?.after.exists && change?.before.exists) {
      // Unfollow — decrement
      await db.doc(`users/${followedId}`).update({
        followerCount: FieldValue.increment(-1),
      });
    }
  }
);
```

## Success Criteria

- All public mutation endpoints (`qr-video` PUT, `batch-render` POST, `tika/sequence` POST) require Firebase Auth or are explicitly scoped with justification and hardened rate limits
- No string interpolation in any query language (HogQL, SQL, or otherwise) -- parameterized queries or strict escaping only
- Firestore rules: zero instances of `allow write: if true` or `allow create: if true` on any collection without a constrained parent path
- `maxAttempts` and similar user-supplied iteration counts clamped to a hard ceiling
- Rate limiter backed by a durable store (Cloudflare KV for general use, Durable Object for auth-sensitive paths)
- Feedback ingest API key moved out of query strings
- `followerCount` updates gated by Cloud Function, not client-side rules
- CSP `unsafe-eval` removed from production builds
