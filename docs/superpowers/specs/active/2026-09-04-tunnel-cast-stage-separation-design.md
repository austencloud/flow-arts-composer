# Tunnel Cast and Stage Separation

**Status:** Approved for implementation on 2026-09-04
**Track:** Tunnel Creator Phase 1 correction
**Precondition for Phase 2:** This correction and Austen's Phase 1 gate must pass first.

## Problem

Tunnel currently asks one legacy value to mean two different things.

- The creator's roster owns authored performers and their choreography.
- `TunnelConfig` was designed for one base sequence and a generated set of
  symmetry copies.
- The renderer fills generated arms by cycling through the authored roster.

That makes a three-person cast require a four-arm configuration. The fourth arm
silently wraps to Performer 1, while the formation editor still describes the
result as `1 x 4 copies`. Reducing the fold to one or two silently fails because
those configurations cannot contain the three authored performers.

This is a model mismatch, not a copywriting defect.

## Outcome

The composition explicitly records every rendered stage instance and which
authored performer drives it. Formation remains the recipe for available
Tunnel positions; it no longer creates anonymous performers behind the roster.

```ts
interface TunnelStageInstance {
  id: string;
  performerId: string;
  arm: number;
}

interface TunnelStage {
  instances: TunnelStageInstance[];
}
```

`arm` addresses one position generated by the existing `TunnelConfig` and
`generateCopyOps` owners. The instance list decides which positions are
occupied. This preserves the canonical transform math without preserving the
old implicit cast assignment.

## Invariants

1. Every authored performer has at least one stage instance.
2. Every stage instance references an existing authored performer.
3. Stage instance IDs are stable across assignment and formation changes.
4. Occupied arms are unique and fit within the formation's available positions.
5. New authored performers receive exactly one stage instance.
6. Additional appearances are explicit additions assigned to a named performer.
7. Removing the last appearance of an authored performer is rejected.
8. Formation changes rebalance occupied arms without changing instance identity
   or performer assignment.
9. The rendered count comes from `stage.instances.length`, never from formation
   capacity.

## Legacy preservation

A version-1 composition is materialized exactly as it rendered before:

- generate every arm from its saved `TunnelConfig`;
- assign arms with the historical round-robin rule;
- persist the resulting explicit stage instances in version 2.

Oregano therefore migrates as `P1, P2, P3, P1`. Its picture does not change.
After migration, the fourth appearance is visible, assignable, and removable.

A collection entry with no composition remains a truthful one-source legacy
tunnel. Its generated arms are likewise materialized before it enters the
creator.

## Creator interaction

The Stage settings formation section becomes composition-aware.

- The headline distinguishes occupied instances from available positions.
- Presets change the position recipe but never add or remove stage instances.
- Presets and position counts that cannot contain the occupied instances are
  visibly disabled.
- The on-stage list names every instance, its position, and its performer.
- Performer assignment uses the canonical segmented-control primitive.
- `Add stage appearance` deliberately duplicates a selected performer.
- Remove is unavailable when an instance is that performer's only appearance.

The legacy primitive tuner remains the correct editor for a classic
single-sequence Viewer tunnel. The creator composes the shared settings shell
with its own stage-aware formation body instead of embedding the legacy tuner.

## Ownership

- `tunnel-stage.ts` owns stage-instance creation, balancing, cloning, and
  migration from generated arms.
- `tunnel-composition.ts` owns the persisted composition schema, validation,
  and resolution into layer plans.
- `tunnel-creator-state.svelte.ts` owns reactive stage editing and keeps roster
  and stage invariants together.
- `TunnelViewController` remains the rendering/presentation adapter. It reports
  occupied rendered instances while exposing formation capacity separately.
- `TunnelArtSettings` remains the settings-shell owner and accepts a composed
  formation body for the creator.

The Stage feature's performer-keyed spot model is the architectural precedent,
not a reusable data type. Stage positions are 3D `x/z` coordinates; Tunnel
positions are canonical pictograph transform arms.

## Persistence boundaries

- Composition schema advances to version 2 and carries `stage`.
- Creator draft schema advances to version 6. Version 5 and earlier migrate.
- Collection and public-revision schemas reuse `TunnelCompositionSchema`, so
  old payloads hydrate through the same migration.
- Public sanitization explicitly whitelists stage instance IDs, performer IDs,
  and arms.
- Save fingerprints include stage assignments.
- `TunnelSnapshot.tunnel.config` remains a compatibility projection for Viewer
  presentation. In the creator, the composition's formation wins whenever the
  two disagree.

## Motion

Adding or removing an instance is intentional structural change. The on-stage
list uses the canonical `growFade` and keyed `animate:flip` owners. The canvas
keeps its existing Tunnel layer arrival/removal motion. Reduced motion collapses
both to their final states through the shared motion helpers.

## Verification

### Domain

- New three-person composition resolves three layers.
- Version-1 three-person/four-arm composition migrates to `P1, P2, P3, P1`.
- Adding and removing appearances preserves stable IDs and roster coverage.
- Formation rebalancing never duplicates an arm or changes assignments.
- Save/public/draft round trips preserve stage instances.

### Runtime

- Oregano reopens with four visible, explicitly named appearances and the same
  rendered picture.
- Removing its second P1 appearance leaves exactly three rendered performers.
- A new third authored performer adds one stage instance, not a fourth copy.
- Invalid position recipes are disabled with an explanation; no control silently
  ignores a press.
- Selection borders and stage animation remain synchronized after reassignment.

### Layout

Verify Stage settings, its list transitions, and the main workspace at
375x667, 960x412, 820x1180, 1440x900, 1920x1080, 2560x1440, 3840x2160, and
200% browser zoom.
